# 為什麼大量工程投入沒有換成完整產品體驗

判讀日期：2026-10-12。依據是[程式規模盤點](REPOSITORY_SIZE_AUDIT.md)、[外部專案比較](EXTERNAL_REPO_COMPARISON.md)、既有產品條件與具名 UX 證據。本文提出產品交付與架構的診斷，供後續規劃討論；沒有新做真人評測、效能分析或跨產品品質排名。

**目前最有證據支持的問題，是交付重心失衡：工程能力持續增加，完整使用者流程的收斂、理解成本與日常價值沒有同步被驗收。** 大量程式因此仍可能只讓系統更完整，沒有讓使用者更容易完成事情。這是我們的開發流程需要修正的地方。

## 證據與診斷

| 問題 | 可核對的證據 | 對產品的影響與判讀限制 |
|---|---|---|
| 工程能力建得比日常使用流程更快 | [Product Roadmap §1](../../00_core/PRODUCT_ROADMAP_POST_REFACTOR.md#1-executive-summary)已指出工程完成度走在日常產品價值之前；盤點中 app、data、ML、UI 合計 687,505 行產品 Python。 | 資料管線、模型、證據和排程各自存在，使用者仍可能需要跨多處理解與組合。Roadmap 是產品問題與成立條件，不以其中舊缺口敘述推定本日全部未完成。 |
| 內部責任集中，使整合與修正成本高 | 推薦畫面 8,755 行，單一推薦 orchestration 函式 1,890 行；37 個產品 Python 檔案至少 3,000 行。盤點已具名指出畫面、policy、來源 identity、非同步任務與保存等職責。 | 修改一段旅程需要同時顧及許多契約，容易以局部補丁繼續擴張。這是可維護性與一致性的風險訊號，尚未逐一證明具體 bug 或重複 runtime 計算。 |
| 局部通過沒有自動形成完整產品接受 | [10/10 複合研究真人驗收](../../06_qa/BALDR_COMPOSITE_HUMAN_CHECK_20261010.md)明確區分自動化七項旅程與尚待取得的真人結果，另排除原來源、部分效能與新 EXE 等範圍。測試／QA Python 有 542,499 行。 | 單元、合成來源、局部接線各有價值，完整旅程還需要同版本、實際入口、使用者判讀與保存回訪的驗收。此例只描述該次收據；目前進展回到最新具名 QA，測試行數也不代表測試有效率已被判定。 |
| 使用者需要承擔部分內部複雜度 | 同份真人操作表需辨認來源頁籤、保存版本、核驗、條件、全域查詢、比較籃與回復原查詢；使用者本次也明確回報入口與長紀錄造成理解負擔。 | 資料與證據契約需要保留，日常介面應把它們轉成目前可做什麼、缺什麼與下一步。這是依操作文字與使用者回饋提出的 UX 假設，需要以實際操作確認。 |

同一套系統可以有很多必要的安全與資料治理程式，卻仍沒有做好「打開後知道今天可以做什麼」。產品價值應以使用者成功完成研究、理解限制、保存結果及回訪來衡量；程式行數與收據數量無法替代這些結果。

## 和外部專案相比，差距應如何理解

[daily_stock_analysis](EXTERNAL_REPO_COMPARISON.md) 的已讀文件圍繞自選股、資料／新聞、報告與推送組成明確旅程。Qlib 的強項是把資料、模型、設定、評估及結果放進一致研究流程；OpenBB 和 vn.py 分別提供可參考的資料接口與事件／桌面模組邊界。它們各自選擇讓主要使用者先完成哪件事，再把支援能力放進相應邊界。

baldr 的定位較廣，增加了整合與解釋成本。這個成本需要由共用契約、清楚的產品入口與完整旅程承擔；僅以功能較多解釋體積，無法解決使用者感受到的落差。外部 repo 的首頁、星數、模型數與宣稱能力，也沒有提供「每個產品都比 baldr 好」或投資效果更好的證據。

## 後續規劃建議

以下是討論用的排序，實作與正式優先序仍依產品 Roadmap、6M Roadmap 及使用者後續選定的範圍。

1. **先定義三條必須順利完成的旅程。** 首次安裝並理解資料／排程狀態；開啟今日研究並理解理由、風險與缺件；保存研究後能在觀察清單與歷史重新開啟。各自用現有來源和已成立的產品資格驗收，不因畫面完成而擴大正式建議資格。
2. **把旅程成功納入交付條件。** 以同一版本核對入口、等待與失敗提示、結果可讀性、保存及重啟回訪；記錄使用者是否需要開發者協助。局部測試繼續覆蓋契約，產品驗收補上它們沒有回答的問題。
3. **依造成阻礙的責任重構。** 先沿旅程定位問題，再拆分大型畫面與 orchestration 中的呈現、資料取得、任務控制及保存責任。驗收目標是步驟更清楚、跨頁狀態一致、恢復可靠與修正成本下降；LOC 只作輔助指標。
4. **讓內部狀態轉成可理解的下一步。** 日常畫面先回答資料是否可用、結果用途、限制與可做的操作；需要追溯時再開詳情。文件以短入口連到 Scoped SSOT 與具名證據，歷史紀錄留在索引後方。
5. **持續核對是否增加實際價值。** 新資料源、模型、Agent 或頁面先說明它改善哪條旅程、如何驗收，以及維護成本。已有功能未形成穩定旅程時，優先完成它們的整合與接受。

## 仍未知的問題

- 同一操作是否重複 SQL、指標計算、hash、模型推理或 UI 轉換，仍需限定操作下的 tracing／profiling；本次 AST 比對不能回答。
- 哪些程式已無 caller、哪些研究工具可退役，仍需依賴及保存責任核對；本次沒有清理裁決。
- 三條旅程各自卡在哪一步、實際耗時、錯誤頻率與理解成本，需要同版本使用者驗收；本文沒有編造測量結果。

本次先保存問題、證據與規劃依據。後續沿[基線使用規則](README.md#這份基線能用多久)做增量確認，直到核心流程或模組責任真正重構，再建立新盤點。
